# 计划：把工具外壳的颜色收进 token 层

- 状态：P0–P3 完成（2026-08-19），P4 待确认
- 日期：2026-08-19
- 范围：`styles.css` 里工具外壳（chrome）的颜色。不包括 Preview。
- 目的：为「chrome 黑白化 + 左右分栏重构」铺路。**P0–P3 不改任何视觉。**

## 为什么现在改不动

实测 `styles.css`：

- `--panel` 定义了但使用 **0** 次，`--canvas` 1 次，`--ui-highlight` 1 次；
- 与此同时有 **68 处硬编码 hex**；
- `#fffaf2`（暖奶油）出现 25 次，`#f5f4ec` 7 次；
- 另有 `#f4efe6`、`#f4eadb`、`#e8ddcc`、`#e5ded2`、`#ece9df` 等十几个只用一次的邻近暖色。

也就是说 chrome 的颜色根本不在变量里。现在「改成黑白」等于一次 60 多处的手工替换，做完没人能验证漏没漏。

## 硬边界：不许碰 Preview

`styles.css` 同时装着两样东西：

1. **chrome** —— 工具自己的界面，颜色目前是硬编码的；
2. **Preview** —— `.site-*` 那批规则，由导出的 website token 名驱动，例如 `var(--surface-page)`、`var(--action-primary-background)`。

Preview 必须保持彩色，而且必须继续由导出的 token 名驱动，这样预览页和导出结果才不会漂。

**chrome token 和 website token 不共用任何名字。** chrome 侧统一加 `--ui-` 前缀；任何一条 chrome 规则都不许引用 `--surface-*` / `--content-*` / `--action-*` / `--feedback-*`。

## 阶段

### P0 盘点
把 68 处硬编码逐一归类到语义槽位：页面底色、卡片底色、内嵌底色、主文字、次文字、弱文字、分隔线、边框、强调色、状态色。产出一张对照表。预计大部分只用一次的暖色可以合并进已有槽位。

**P0 结果（2026-08-19 完成）**

实测 `styles.css` 703 行：**92 处**硬编码颜色，**65 个**不同的值。三个发现改变了后续做法：

1. **`.site-*` 区间（323–386 行）里硬编码颜色数量是 0。** Preview 已经完全由导出的 website token 驱动。硬边界不需要靠人守，它本来就是干净的——P2 的风险比原先估计的低。

2. **`#fffaf2` 出现 25 次，但它在做两件事。** 一是浅色抬升表面（输入框、卡片、菜单、`.saved-pair`、`.suggestion`），二是深色底上的反色墨（`.step-dock`、`.global-target`、`.step-link`、`.button.primary`、`.toast`）。同一个 hex，两种语义。任何全文替换都会把这两件事焊死在一起，而黑白化恰恰需要它们分开——这就是这次重构存在的理由。

3. **右下角 Steps 窗口是浅色界面里的一座深色岛。** 它自带一套子调色板：`#29251f` 底、`#39342d` 抬升层，外加 11 个不同透明度的白（`.06` 到 `.84`）和 6 个不同透明度的暖白。黑白化时这块区域是唯一需要真正做决定的地方，其余部分基本是机械换值。

另外，65 个值里大部分是**同一个基色的不同透明度**：`255,255,255` 有 11 档、`180,76,56` 有 6 档、`169,107,33` 3 档、`41,37,31` 3 档、`35,30,25` 3 档、`54,45,35` 4 档。所以 token 集不需要 65 个，只需要十几个基色，透明度留在使用处——透明度是用法决定，不是调色板决定。

**修正原计划一条：不要在 P2 合并那些只用一次的暖色**（`#f4efe6`、`#f4eadb`、`#e5ded2`、`#ece9df`）。合并会改变像素，与「纯重构」冲突；而 P4 黑白化本来就要把它们全部换掉，现在合并是白做。P2 保持 1:1，合并候选记在这里，留到 P4 一起处理。

### P1 定义 chrome token 集
在 `:root` 定义一组 `--ui-*` token，数量要小。现有的 `--ink`（15 次）、`--muted`（45 次）、`--line`（34 次）已经在用，保留并入新命名。

**P1 结果（2026-08-19 完成）**：已在 `styles.css` 的 `:root` 定义，分六组——浅色表面、深色 dock、墨色、强调、状态、透明度基色（写成 `rgb(var(--x) / <alpha>)`）。`--ui-surface` 和 `--ui-ink-inverse` 取值相同但分开定义，就是为了 P0 发现的那个双重身份。

旧名字（`--ink` / `--muted` / `--line` / `--panel` / `--canvas` / `--good` / `--warn` / `--bad` 等）全部改成指向新 token 的别名，所以这一步是纯增量，零视觉变化。P2 每迁移完一个区块就删掉对应的别名。

### P2 逐区块替换
不要一次性全文替换。按区块推进，每块替换完视觉必须逐像素不变——这一阶段是纯重构。

**P2 结果（2026-08-19 完成）**：118 处替换，`:root` 之外已无任何裸 hex 或 `rgba()`。

两条按声明属性区分语义的规则处理了 P0 发现的双重身份：`#fffaf2` 在 `background` 上解析成 `--ui-surface`，在 `color` / `stroke` 上解析成 `--ui-ink-inverse`；`#29251f` 只在 `background` 上是 `--ui-dock`，其余（含 `border`）都是 `--ui-ink`。

验证方式是同一次页面加载内的 A/B：固定视口 1280×900，抓取全部 1173 个元素 × 9 个颜色属性的 computed value，换回原始 `styles.css` 再抓一次，逐字段比对——**差异 0**。

（过程中踩到一次假阳性：视口宽度为 0 时所有 `max-width` media query 同时生效，`.wcag-level` 的边框从 right 跳到 bottom，看起来像回归，其实规则一个字没动。度量前必须先确认 `innerWidth` 不是 0。）

### P3 加静态检查
在 `tests/static-contract.test.mjs` 里加两条：chrome 区域不允许出现裸 hex；`.site-*` 规则不允许引用 `--ui-*`。

这条检查是整次重构唯一的长期价值——它保证外壳不会再退化回硬编码。

**P3 结果（2026-08-19 完成）**：两条断言已加入，并且都做了反向验证——往 chrome 塞一个 `#abcdef` 会失败并报出该值，往 `.site-link` 塞一个 `var(--ui-ink)` 会失败并报出该选择器。一条不会失败的检查没有价值，所以这一步必须反着测一次。

另外改了一条既有断言：`.pair.needs-work` 原本 pin 死了字面量 `rgba(180,76,56,.08)`，现在改成 token 形式。

### P4 页面重构 + 黑白化（另起一份计划）

P4 从「换一组值」扩大成了**布局重构**。目标形态：

- **右半边固定预览。** Preview 不再是往下滚才看得到的一个 section，而是常驻右半屏。改左边任何一个选择，右边立刻看到结果——这才是「点点点就能生成一套颜色系统」该有的反馈闭环。预览保持彩色，继续由导出的 website token 驱动。
- **左半边走 x.com 风格。** 黑白灰为主，彩色只出现在「你下一步该按的东西」上。
- **左侧先保留现有步骤**（Quick start / Context / Colors / Website tokens），不在这一步做减法。缩减是后续的事，先把布局和视觉立住。

**Steps 窗口的去向已定（2026-08-19）：整个删掉。** 不是搬家，是取消。

替代它的是每个步骤标题上的一个**空心圆**：没有数字，点击折叠整个 step section，单色，未动过的步骤呼吸。顺序不再由编号承载，改由左栏从上到下的排列本身承载——这是一次真实的减法，接受。

原来住在 dock 里的 WCAG target 是全局控件，随 dock 一起无家可归，现在**前置到左栏 01 之前**独立成块，不固定、随页面滚动。它管着下面每一个测量结果，所以在第一步之前声明，而不是塞进某一步里面。

**P4b 已实现（2026-08-19）**，在 P4a 之前落地：

- `.step-dock` / `.step-link` / `.global-target` 的全部 30 条 CSS 规则、dock 的 DOM、`setActiveStep` / `IntersectionObserver` 滚动追踪、以及 7 个只服务 dock 的 i18n key，全部移除。
- 空心圆用 `.step-mark::before` 画：15px 圆环、2px `--ui-ink` 描边。**单色是有意的**——chrome 里彩色只意味着「下一步按这个」，而步骤标题不是那个东西。
- 呼吸的语义是「还没看过」：section 初始 `data-touched="false"`，section 内任何 `pointerdown` 或 `focusin` 都把它置为 `true`，呼吸永久停止。
- 折叠时圆环 `border-width` 从 2px 变 7px，接近实心点，作为「已收起」的形状信号，不靠颜色。
- `prefers-reduced-motion` 下呼吸动画关闭——一个常驻脉动的元素必须尊重这个设置。
- Role checks 的「编辑这个角色」原本调 `setActiveStep`，现在改调 `revealStep()`：滚过去之前先展开目标 section，否则会滚到一个折叠的标题上，看起来像什么都没发生。

**同一轮的界面复查修了四处**（`/better-interface` quick 模式）：

- **焦点环不合格。** `rgb(var(--ui-accent-rgb) / .38)` 在白底上渲染成 `#DEB5AB`，实测 **1.86:1**，低于 WCAG 1.4.11 对非文本指示器要求的 3:1。改成实色 `--ui-accent-strong`，6.30:1（卡片上 5.96:1）。白底放大了这个问题——原来的奶油底也不合格，只是没这么刺眼。
- **控件边框不合格。** `--ui-line`（ink 16%）渲染成 `#D9D9DA`，**1.41:1**。新增 `--ui-line-strong`（ink 46%，3.08:1）给输入框和下拉触发器；纯装饰性分隔线继续用 `--ui-line`，因为 1.4.11 不管装饰线。
- **四个折叠按钮同名。** 都是 `aria-label="Collapse this step"`，读屏用户听到四遍一样的名字。改成 `aria-labelledby` 指向各自的步骤标题（APG disclosure 模式），现在分别是 Quick start / Context / Colors / Website tokens，状态由 `aria-expanded` 单独承担。
- **分栏断点定错了。** 1200px 以下工作区放不下：1024px 时步骤内容列只剩 216px，而 50–950 色阶条需要 588px，实测 `scrollWidth` 溢出 2.7 倍。断点从 900px 提到 1200px。
